# Lane 02 — workerd and Durable Objects on your own metal

Research date: **2026-10-29**. All repo facts were fetched that day through the GitHub REST proxy (`forge.web.pkgforge.dev/github/...`, which mirrors `api.github.com`), raw files at `main` and at release tags via `raw.githubusercontent.com`, and `developers.cloudflare.com`. Everything else is labelled. Note that lane 11 also covers `workerd` from an OSS-inventory angle; this lane is scoped to the **stateful** question — can you run Durable Objects off Cloudflare, and what is missing.

## Verdict

Yes, workerd runs standalone, and as of 2026 it runs Durable Objects on your own disk — but *standalone* means **one process, one thread, one machine**, which is not a Durable Objects deployment: DOs exist precisely so that one named object is served exactly once no matter how many machines you have. The distributed half is brand new and unreleased: PR #7994, "Cluster workerd processes over a shared bucket", merged into `main` at **2026-10-29T03:11:43Z** — about two hours after the newest release `v1.20261029.1` was cut — and its own author states that objects currently ack a write only after a full sync to the bucket, "much too slow and expensive for most uses", with alarms not yet wired up. So today the only thing that actually delivers distributed, durable, fault-tolerant Durable Objects on your own metal is **`denoland/celld`**, Apache-2.0, 6,169 stars, v0.6.3, which is a serious piece of engineering (SQLite-per-object, S3 conditional-write leases, fencing epochs, RPO=0 output gate) and is simultaneously disqualified as a *platform* by one line in its own limitations doc: "A fleet runs one application." The single most important caveat is that **every path here is beta or experimental and single-tenant** — celld is a v0.6.x beta with pull requests disabled, workerd's cluster mode is days old and `--experimental`, and both require you to supply an S3-compatible bucket with true conditional-write semantics, which quietly rules out MinIO-in-production, Backblaze B2, Hetzner Object Storage and DigitalOcean Spaces.

## Findings

### Can workerd run standalone outside Cloudflare? Yes, and Cloudflare says so explicitly

The README's first listed use case is *"As an application server, to self-host applications designed for Cloudflare Workers"* (VERIFIED, https://github.com/cloudflare/workerd). Kenton Varda, workerd's lead, is unambiguous: *"You can definitely run workerd in production on your own machines and some people do. The biggest catch is that workerd's implementation of Durable Objects currently doesn't work across multiple machines"* (VERIFIED, secondary — HN comment, https://news.ycombinator.com/item?id=48435372, 2026-06-07).

Mechanics: you run `workerd serve config.capnp`, where the config is a Cap'n Proto schema (`src/workerd/server/workerd.capnp`, 1,276 lines). Releases are cut roughly daily — `v1.20261029.1` on 2026-10-29T00:53:29Z (VERIFIED, GitHub releases API) — and there are prebuilt binaries plus npm packages, so Bazel is only needed if you build it yourself. There is also a `Dockerfile.release` in the repo root that builds a static `workerd` binary from a `node:trixie` + LLVM 22 builder stage (VERIFIED, https://raw.githubusercontent.com/cloudflare/workerd/main/Dockerfile.release) — but I found **no documented official published image**; what exists is community packaging (see the Docker section below).

The repo also ships a `wrangler.jsonc` entry point, which sounds like the thing you want and is not: *"The supported fields are `name`, `main`, `compatibility_date`, `compatibility_flags`, `vars`, `durable_objects`, `migrations`, `no_bundle` and `$schema`; any other field is an error."* (VERIFIED, workerd README). Nine fields, no bindings. Real deployments are hand-written Cap'n Proto, generated by your own control plane.

### What is missing, part 1: the Durable Object storage backend

This is the crux, and it is best read straight off the schema. `durableObjectStorage` is a union of exactly three things (VERIFIED, `workerd.capnp`):

- `none` — no DOs.
- `inMemory` — *"The `state.storage` API stores in-memory only. All stored data will persist for the lifetime of the process, but will be lost upon process exit. … This mode is intended for local testing purposes."*
- `localDisk` — *"** EXPERIMENTAL; SUBJECT TO BACKWARDS-INCOMPATIBLE CHANGE ** Durable Object data will be stored in a directory on local disk."* One `.sqlite` file per object, plus `-wal`/`-shm`.

So on a single node you get real, durable, SQLite-backed DOs. What you do **not** get is replication, placement, or failover — the object lives on the disk of the one process that owns it. PR #6780's own description states the historical position plainly: *"workerd has always supported running Durable Objects for the purpose of local testing, but only within the scope of a single instance running on a single thread. … in production, you probably want to utilize more than one thread on one machine. For stateless Workers, this could be done just fine … But doing this completely broke the model of Durable Objects"* (VERIFIED, https://github.com/cloudflare/workerd/pull/6780).

The fix landed in two attempts. The first, #6780 ("Make self-hosted Durable Objects scalable across a cluster"), was **closed unmerged on 2026-09-11T22:27:23Z** after four months; its design used NFSv4 for shared state, which drew the obvious criticism on HN (*"bummer this expects NFS"*) and a concession from Kenton that *"I could imagine a follow-up to support LiteFS instead of NFS"* (VERIFIED, secondary — https://news.ycombinator.com/item?id=49191649). The second attempt, #7994, merged 2026-10-29T03:11:43Z and is explicitly derived from celld: *"This is the beginning of merging celld's functionality into workerd. … Each Durable Object has one owner at a time, requests reach it from any process, and when its owner dies another process picks it up from the bucket. Objects log their commits to the bucket as Cap'n Proto frames of SQLite pages (`frames.capnp`) and compact the log into snapshots. For now an object acknowledges a write only once it is fully synced to the bucket; that is much too slow and expensive for most uses. Next PRs will ack writes with the cluster and add support for alarms."* (VERIFIED, https://github.com/cloudflare/workerd/pull/7994).

The config surface for that is `Config.cluster`, marked *"Set when this instance should join a cluster. Requires `--experimental`"*, and its doc comment is a precise description of the design: *"The cluster's shared state lives in an S3-compatible bucket: each instance renews a lease record naming its address, and each Durable Object's owner is a record claimed by a conditional write. Taking an object over from an owner whose lease expired bumps its ownership epoch. … the bucket's copy of an object replaces the instance's, so a `localDisk` already holding Durable Objects from before cluster mode is refused at startup"* (VERIFIED, `workerd.capnp` lines 104-124).

Two things to be blunt about. First, **no shipped binary contains this**: `grep -c ClusterConfig` returns **0** at tag `v1.20261029.1` and **3** at `main`, checked directly today (VERIFIED, raw file at both refs). To use it you build from `main`. Second, the inter-node channel is unauthenticated-but-unencrypted: *"Holders of `key` get full access to every service in the process through it, and its traffic is not encrypted: only the cluster's instances should reach it, on a private network (a VPC, WireGuard, Tailscale). A public IP is refused unless `unsafePublicAddress` is set"* (VERIFIED, same file). That maps well onto this study's Cloudflare Tunnel/Mesh constraint — the cluster network is a private overlay, not a public listener — but it is your overlay to build.

### What is missing, part 2: alarms

Alarms are **implemented** in workerd — `src/workerd/api/actor-state.h` declares `getAlarm`, `setAlarm`, `deleteAlarm` and exposes them as `JSG_METHOD`s on the state API (VERIFIED, https://raw.githubusercontent.com/cloudflare/workerd/main/src/workerd/api/actor-state.h, lines 61/139/141 and 320-322/420-422). So single-node workerd gives you `storage.setAlarm()` and the `alarm()` handler, which is the piece people assume is Cloudflare-only.

In **cluster** mode they are not there yet — the #7994 body says "Next PRs will … add support for alarms" (VERIFIED, same PR). That matters more than it sounds: celld implements KV expiry, `@cloudflare/containers`' `sleepAfter`, queue retries and Workflows' durable sleeps all on top of alarms. Any DO code you write that relies on a timer is single-node-only on workerd today.

### What is missing, part 3: KV, R2, Queues, D1 are empty sockets

The schema has binding *types* but no implementations, and the doc comments say so:

- `kvNamespace @11 :ServiceDesignator` — *"A KV namespace, implemented by the named service. … Requests to the namespace will be converted into HTTP requests targeting the given service name."*
- `r2Bucket @12 :ServiceDesignator` — *"R2 bucket binding. Similar to KV namespaces, this turns operations into HTTP requests aimed at the named service."*
- `queue @15 :ServiceDesignator` — *"A Queue binding, implemented by the named service."*

(VERIFIED, `workerd.capnp` lines 524-542.) In other words workerd gives you the JavaScript-visible object and expects *you* to run an HTTP service that speaks the internal KV/R2 wire protocol. That protocol is not documented in the repo — I looked, and the schema comment is the whole specification (BELIEVED: no spec exists; nothing in `docs/` covers it).

D1 is worse: **there is no `d1` binding in the config schema at all**. The binding union is `text, data, json, wasm, cryptoKey, service, durableObjectNamespace, kvNamespace, r2Bucket, obsolete0, queue, analyticsEngine, hyperdrive, durableObjectClass, workerdDebugPort` — no D1, no Vectorize (VERIFIED, `workerd.capnp` lines 605-630). D1 in workerd is a TypeScript shim, `src/cloudflare/internal/d1-api.ts`, whose header literally reads *"Binding contract to create a custom binding"* over a `D1BindingService = { query(params: QueryRequest) }` RPC (VERIFIED, https://raw.githubusercontent.com/cloudflare/workerd/main/src/cloudflare/internal/d1-api.ts). So "D1 support" means "a JS wrapper expecting some service to answer SQL queries" — you write the service.

Consequence for this study: workerd alone gives you the **edge runtime** and the **DO primitive**, and nothing at all for object storage, KV, queues or SQL. Those are separate lanes' problems, and workerd will not meet you halfway.

### What is missing, part 4: it is not a sandbox, and not a multi-tenant platform

If the dashboard/SPA is the only Cloudflare-hosted piece and everything else is yours, then "run untrusted code" may or may not be in scope — but if you ever host someone else's Worker, this is disqualifying without extra work. The README states: *"**WARNING: `workerd` is not a hardened sandbox** … `workerd` on its own does not contain suitable defense-in-depth against the possibility of implementation bugs. When using `workerd` to run possibly-malicious code, you must run it inside an appropriate secure sandbox, such as a virtual machine."* (VERIFIED, https://github.com/cloudflare/workerd). The same warning is repeated verbatim on the Miniflare docs page (VERIFIED, https://developers.cloudflare.com/workers/testing/miniflare/).

There is also no limit enforcement in the OSS server, which is easy to miss: the repo's own `AGENTS.md` describes `src/workerd/server/` as *"the single-tenant server"* which *"keeps the single-tenant policy objects … the unlimited `LimitEnforcer`, … the null `IsolateLimitEnforcer`"* (VERIFIED, quoted in lane 11 from `src/workerd/server/AGENTS.md`; I did not re-fetch this file in this lane). No CPU cap, no memory cap, no per-isolate limits. Hosting third-party code means building that yourself.

### denoland/celld deep dive: the only working distributed DO today

**Facts.** `denoland/celld`, Apache-2.0, Rust, created 2025-04-25, 6,169 stars, 423 forks, 78 open issues, last push 2026-10-21T21:12:49Z, latest release `v0.6.3` published 2026-10-21T21:12:44Z (VERIFIED, GitHub API). Description: *"self-hosted, distributed Durable Objects"* (VERIFIED, repo metadata).

**What it is.** *"celld is an open-source daemon that runs a Cloudflare Workers application on your own machines: Workers, Durable Objects, KV, Queues, D1, R2, Workflows, Cron Triggers, and static assets, deployed from the `wrangler.json` that you already have. Each object is a cell: a named server with its own SQLite database. celld stores the long-term state in your S3-compatible, Google Cloud Storage, or Azure Blob Storage bucket. It needs no serving control plane or consensus service."* (VERIFIED, README). Note it is **not** built on workerd — it embeds V8 directly (*"Every node embeds V8 and executes Wrangler bundles"*) and reimplements the Workers API surface itself. That is a different risk profile from workerd: it is a from-scratch runtime by the Deno team, not Cloudflare's own code.

**The distributed protocol, briefly.** A node claims a cell by conditional-write of `cells/<cell>/own.json` into the bucket; every activation bumps a fencing epoch that appears in the storage prefix, so a node that lost ownership can only write into a superseded prefix. Commits are captured in SQLite's LTX replication format and uploaded to `cells/<cell>/ltx/e<epoch>/`. Durability is proven either by the bucket (single node) or by one or two peers holding the data on local disk (multi-node), and an output gate holds every response until a durability proof covers every write the response can reveal. That is a genuine RPO=0 design, and the docs are unusually explicit about failure modes — including what happens when someone puts a lifecycle rule on the bucket and destroys an ownership record (*"celld ownership record lost"*, then refusal to acquire the cell) (VERIFIED, https://raw.githubusercontent.com/denoland/celld/main/docs/guarantees.md).

**Performance, in its own numbers.** *"A write to a region-local store takes about 90 ms. One loaded lab fleet measured about 600 ms against a store that was not region-local, and about 25 ms once a second node held the write."* (VERIFIED, README). Two things follow: single-node celld costs ~90 ms per write, which is catastrophic for chatty DO workloads and fine for low-rate coordination; and **you should run at least two nodes** or every write pays a bucket round trip. This is a design where the object-storage latency is on the critical path of your Durable Object.

**Coverage.** The compatibility matrix is remarkably complete: Workers **Yes**, Durable Objects **Yes**, Durable Object Facets **Yes**, Static assets / Cron / Dynamic Workers / KV / Queues / D1 / Workflows / R2 **Yes**, Containers **Experimental**, Python Workers **Partial** (Pyodide 0.28 `fetch` handlers), and Workers AI / Vectorize / Hyperdrive / Browser Rendering / Email Workers **No** (VERIFIED, https://raw.githubusercontent.com/denoland/celld/main/docs/cloudflare-compat.md). `BroadcastChannel` is **No**; `tail` and `email` handlers are unavailable; `node:crypto` lacks Diffie-Hellman, streaming signatures, ciphers, RSA-PSS and DSA; `node:zlib` is sync-only; `node:fs` exposes only an empty request-local `/tmp` and a read-only `/bundle`. It also runs `@cloudflare/containers` and `@cloudflare/sandbox` *as published*, including `sleepAfter` alarms — which is more than workerd can claim today (VERIFIED, https://raw.githubusercontent.com/denoland/celld/main/docs/services/containers.md).

**Why it fails as a platform — the decisive line.** From `docs/limitations.md`: *"A fleet runs one application. celld has no account service, multi-tenant scheduler, or managed ingress."* (VERIFIED). Read that against this study's goal. celld gives you a Workers/DO runtime for **one** application per fleet, and the fleet's identity is a bucket plus a shared key. It is not a hosting platform; it is a deployment target. If the product is "self-hosted replacement for Workers + DO for our own apps", celld is close to turnkey. If the product is "a platform on which many tenants deploy Workers", celld is one fleet *per tenant*, with a bucket and a set of nodes each — which is an operational cost model you should price out before committing.

**Other blunt gaps** (all VERIFIED, `docs/limitations.md` unless noted):
- *"celld does not terminate TLS. Terminate public TLS at an ingress proxy."*
- *"Peer traffic is plaintext HTTP. The fleet HMAC authenticates tunnel establishment and control requests but does not encrypt data, so the network must provide confidentiality."* Same shape as workerd's cluster mode: your WireGuard/Tailscale/Mesh overlay is load-bearing.
- *"celld v0.6.3 is a beta release"* — and the version is 0.6.x, six months after a 0.5.x.
- *"Pull requests are disabled. Coding agents make it too easy to send a large, low-context change…"* — contributions by `git format-patch` email to the maintainer only. Bus factor is effectively one person at Deno.
- Windows unsupported; binaries for Linux x86-64/ARM64 and Apple Silicon only.
- Balancing is by cell count weighted by CPU, not by actual load, and *"It moves only hibernated cells"*.
- Azure managed identity from App Service or Container Apps does not work.

**Kubernetes.** There is no Helm chart, no operator, and no manifests in the repo — the tree is `.github/`, `crates/`, `docs/`, `examples/`, `Dockerfile`, `Cargo.toml` (VERIFIED, contents API). What the docs give you is a paragraph: *"Run celld under a supervisor that restarts the process, such as systemd, Docker with a restart policy, or Kubernetes. A node that loses its lease fences itself and exits, and without a restart the fleet loses that capacity. The supervisor must restart without an attempt limit and wait at least one lease lifetime between attempts."* (VERIFIED, `guarantees.md`). Plus a note that on EKS it reads Pod Identity credentials (VERIFIED, README). So: a `Deployment`/`StatefulSet` with `restartPolicy: Always`, `--advertise` set to a stable per-pod address (needs a headless Service or a StatefulSet ordinal DNS name), and port 8081 kept off the public network. That is a day of work, not a product.

### The sleeper constraint: celld's bucket is not any bucket

This is the finding most likely to break the overall architecture, so it gets its own section. celld requires four properties from the object store: *"A conditional create: the write must fail when the object exists. A conditional overwrite: the write must fail when the object changed after the read. Read-after-write consistency … Ranged reads"* (VERIFIED, `guarantees.md`). Then, explicitly:

- Qualified: *"The qualified stores are Amazon S3, Cloudflare R2, Tigris, Google Cloud Storage, and Azure Blob Storage. The release tests run against R2"* (VERIFIED).
- Disqualified: *"Backblaze B2, Hetzner Object Storage, and DigitalOcean Spaces do not implement the required conditional writes, so two nodes can own one cell on them."* (VERIFIED).
- MinIO: *"MinIO (the community edition) passes the storage test but is not qualified for production. RELEASE.2025-09-06T17-38-46Z answers the conditional create of an absent object with `NoSuchKey`, so the first deploy fails (denoland/celld#162). Use RELEASE.2025-09-07T16-13-09Z or later."* (VERIFIED).
- And: *"A store that accepts the conditional headers but ignores the condition fails late and silently, so run the storage test."* (VERIFIED).

Why this matters beyond celld: **the same requirement will apply to any self-hosted DO layer** — workerd's `ClusterConfig` uses the identical mechanism (*"a record claimed by a conditional write"*). So whichever S3 replacement the object-storage lane picks, it must implement `If-None-Match: *` and `If-Match` **correctly**, plus read-after-write consistency and range reads. Self-hosted MinIO is "passes the test, not qualified"; the honest reading is that a self-hosted object store is a *correctness risk* for the DO layer, not merely a performance one, and celld's own docs tell you it fails silently. The cheapest safe configuration is a managed S3/R2/GCS bucket as the DO durability substrate even if bulk objects live on your own metal — which is an argument for splitting "the DO bucket" from "the R2 replacement" rather than unifying them.

Also worth flagging: celld's guarantees *depend* on bucket correctness in a way HN commenters immediately noticed. One commenter wrote that celld's segment writes *"looked like plain, unconditional PUTs with no epoch check"* (VERIFIED, secondary — https://news.ycombinator.com/item?id=49205618). The docs answer this precisely: *"The replicator copies each cell's SQLite data to `cells/<cell>/ltx/e<epoch>/` with unconditional PUTs. The epoch in the key is the fence: a node that lost ownership can keep writing, but only into a superseded prefix, and a restore selects the current lineage."* So the criticism was about the mechanism, and the mechanism is sound — but it is sound *only because* the ownership record's conditional write is correct. The critique is really "this is a single point of correctness in your bucket", which is true and is why `celld diagnose` exists.

### miniflare: a simulator, and Cloudflare says so twice

Miniflare is *"a simulator for developing and testing Cloudflare Workers. It is written in TypeScript and uses a local `workerd` process to implement Workers runtime APIs."* (VERIFIED, https://developers.cloudflare.com/workers/testing/miniflare/). It supports KV, R2, D1 and DOs — but via *"local storage simulators"* (VERIFIED, same page, storage section), i.e. files on the developer's disk. Two explicit warnings on the same page: *"Miniflare is not a hardened sandbox. Do not use Miniflare to run untrusted or potentially malicious Worker code directly on your machine."* and *"Miniflare is not a security boundary for untrusted code."* (VERIFIED).

So: miniflare is a **dev/test** tool, not a deployment target. Its value to this study is that it proves the workerd config can be driven from a Wrangler-style config, and it is the reference implementation of KV/R2/D1 simulators that workerd lacks — if you need to build those HTTP services, Miniflare's implementations are the closest thing to a spec. Do not put it in production; it has no replication, no fencing, no auth, and the docs say it is a simulator.

### Docker images and Kubernetes operators: nothing production-grade exists

Searched GitHub repositories for `workerd+kubernetes`, `workerd+docker`, `durable+objects+selfhosted` (VERIFIED, GitHub search API via proxy). What came back:

- `Cyb3r-Jak3/docker-workerd` — 15 stars, Apache-2.0, last push 2023-02-11. Stale.
- `pmbanugo/workerd-docker` — 19 stars, Apache-2.0, 2023-12-15, and it is a URL-shortener demo, not infrastructure.
- `frafra/workerd-docker` (2022), `Dcard/docker-workerd` (2024), `zbndm/workerd-docker` (2022), `getchoo-archive/workerd-docker` (2024) — 1-2 stars, effectively abandoned.
- `solcreek/groundflare` — 5 stars, MIT, last push 2026-09-09, npm `groundflare`. This is the most interesting one: *"Run any Cloudflare Worker on your own hardware. Same code, your machine, no vendor lock-in."* It provisions a VPS on Hetzner/DigitalOcean/Linode/Vultr, runs cloud-init, and starts `workerd` (or a Bun track) under systemd with Caddy for Let's Encrypt TLS (VERIFIED, https://raw.githubusercontent.com/solcreek/groundflare/main/README.md). It also ships a SeaweedFS sidecar for a self-hosted R2 (`env.MEDIA.put/get/...`) and claims *"1002 tests across L1 pure-function / L2 workerd-driven / L3 real-SeaweedFS layers"* (VERIFIED, same README). But: 5 stars, one author, VPS-shaped not Kubernetes-shaped, and it solves deployment ergonomics rather than DO distribution.

**No Kubernetes operator for workerd exists.** The `workerd+kubernetes` search returned generic "what is a Kubernetes operator" explainers and one workerd URL-shortener demo (VERIFIED). Likewise no operator or chart for celld. If this study wants a k8s-native DO layer, the operator is a thing you would write — and given that both workerd cluster mode and celld already expose a "node that advertises an address and gets restarted by a supervisor" model, the operator is genuinely thin (StatefulSet + headless Service + a bucket secret + readiness on the internal listener), but it does not exist off the shelf.

### Containers and heavy CI: this is the wrong layer, and celld says so

For the study's "heavy CI and long-running containers" workload, neither workerd nor celld is the answer, and both are honest about it.

workerd's `containerEngine` is `none` or `localDocker`, and `localDocker` is documented as *"Only used for local development and testing purposes"* (VERIFIED, `workerd.capnp`). celld's Containers support is marked **Experimental** and carries an unusually candid isolation warning: *"Under the default runtime, a container shares the kernel of the node and is not a virtual machine. celld drops all Linux capabilities, sets `no-new-privileges`, keeps the default seccomp profile of the daemon, limits the container to 1024 processes…"* (VERIFIED, `docs/services/containers.md`). It also requires *"a Docker or Podman daemon"* on every node that serves a container class, installs nftables rules via a privileged one-shot container, and *"The container disk is ephemeral, so durable state belongs in the storage of the object or in another binding."*

A CI job is the exact workload this handles worst: long-running, disk-hungry, needs a persistent workspace, needs a VM-grade isolation boundary if you run untrusted PRs, and needs to not be killed when a DO hibernates or rebalances. The container is *supervised by a Durable Object*, so it inherits the object's placement and lifetime — which is the opposite of what a CI runner wants. Route heavy CI to lanes 04/05 (microVM / orchestrator); use workerd/celld for the control plane's own API surface, webhooks, and coordination state, not for the jobs.

### Real-world self-hosting reports

Honest summary: **there are no credible production write-ups**. What exists is (a) Cloudflare's own "some people do" (Kenton, above, with no names or numbers), (b) launch-thread enthusiasm, and (c) vendor-adjacent blog posts.

- The celld launch thread, 286 points, 54 comments, 2026-08-05 (VERIFIED, https://news.ycombinator.com/item?id=49185430). The technically substantive comments are all architecture, not operations: *"workerd is missing the scheduler - the thing that allows it to operate across nodes. Durable Object storage are just local sqlite databases. celld is the full distributed system (albeit single tenant)"* (VERIFIED, comment 49190282) — which is a correct and useful one-line summary of the whole lane. Kenton's reply in the same thread: *"You beat us to it! Been meaning to land this but got distracted"* and *"But yes, celld is definitely ahead of us here. No doubt about that."* (VERIFIED, comments 49190321 and 49191649). That is Cloudflare's own DO/runtime lead conceding the point — the strongest single piece of evidence in this lane.
- The recurring criticism in that thread is cost, not correctness: *"Durable Objects can be quite expensive. whenever i get too excited about em all it takes is a little time trying to price it out to calm me down"* (VERIFIED, comment 49191579), followed by a rebuttal that running EKS clusters in five regions is itself ~$8,600/yr (VERIFIED, comment 49198982). No one reports having run celld in production.
- Secondary commentary: `flaviocopes.com/celld/` (2026-10-16, "How celld runs Workers on your own infrastructure") and a YouTube walkthrough titled "Self-hosted durable objects are pretty interesting!" — both explanatory, neither an operations report (VERIFIED that they exist and are dated; I did not treat their content as evidence).
- The xda-developers piece "I self-hosted my own Cloudflare Workers replacement" (2026-03-25) is a hobbyist single-VPS account, not a DO deployment, and predates celld's distributed work (VERIFIED existence/date only; secondary).

Treat "some people run workerd in production" as true for **stateless Workers** and unproven for **Durable Objects**. Nobody in public has reported running either workerd cluster mode (impossible — it is hours old) or celld at meaningful scale.

## Rejected options

| option | why rejected |
|---|---|
| **workerd single-node `localDisk` as the production DO layer** | No failover: the object lives on one machine's disk. One node death = data unavailable until the disk comes back. Also marked EXPERIMENTAL in the schema. Fine for `wrangler dev`-shaped work and single-box side projects; not a DO replacement. |
| **workerd `inMemory` DOs** | The schema says it: "All stored data will persist for the lifetime of the process, but will be lost upon process exit … This mode is intended for local testing purposes." Not durable at all. |
| **workerd cluster mode as of today** | Not in any release (0 matches in `v1.20261029.1`), requires `--experimental` and a build from `main`, ack-per-write through the bucket is "much too slow and expensive for most uses" by the author's own description, and alarms are not wired up. Revisit in a quarter; today it is a demo. |
| **miniflare as a deployment target** | Its own docs: "a simulator for developing and testing", "not a hardened sandbox", "not a security boundary for untrusted code". No replication, no auth, no fencing. |
| **NFS-based shared storage for DOs (PR #6780)** | Closed unmerged 2026-09-11 after four months; superseded by the S3-bucket design. NFS also means filesystem-level locks and a single point of failure the study's Tunnel/Mesh topology does not naturally give you. |
| **celld as a multi-tenant Workers hosting platform** | "A fleet runs one application" — no account service, no multi-tenant scheduler, no managed ingress. You would run one fleet + one bucket per tenant, and the bucket must be a qualified store. That is a per-tenant infrastructure cost, not a platform. |
| **celld Containers for heavy CI** | Experimental; container shares the node kernel ("is not a virtual machine"); disk is ephemeral; the container's lifetime is bound to a Durable Object's placement and hibernation. The exact opposite of what a CI runner needs. |
| **Community workerd Docker images as infrastructure** | They are image-only (36★ max), the rest are stale 2022-2024, and none provide config generation, DO distribution, or an operator. |
| **rivet as a drop-in** | Not Cloudflare-API-compatible — a different programming model. Good project (6,484★, actively developed) but choosing it is a rewrite of every Worker and DO you have, which contradicts the "replacement that keeps the code" premise. |

## Open questions

- **Does workerd cluster mode actually work under load?** It merged hours ago and I did not run it. Settled by: building `main`, running 3 nodes against a real S3 bucket, killing the owner mid-write, and measuring ack latency + verifying no lost acknowledged write. Until someone does that, treat #7994 as a design, not a product.
- **Will celld's cluster code stay in celld, or move entirely into workerd?** The PR says "the beginning of merging celld's functionality into workerd". If it all lands upstream, celld becomes a distribution of workerd and the choice collapses to "workerd + your control plane". Settled by: watching the next few workerd releases for `ClusterConfig`, alarms in cluster mode, and peer-ack writes.
- **Does celld's licence/contribution model survive?** Apache-2.0 with pull requests disabled and patches by email — a fork is legal but the project is effectively one maintainer at Deno. Settled by: contributor count in the API and whether a second committer appears over the next two quarters.
- **Which self-hosted object store actually satisfies celld's conditional-write contract in practice?** The docs qualify S3/R2/Tigris/GCS/Azure and reject B2/Hetzner/DO Spaces; MinIO "passes the test but is not qualified". Nobody has published a long-run MinIO or SeaweedFS + celld report. Settled by: running `celld diagnose` plus a multi-day two-node soak against each candidate (MinIO latest, SeaweedFS, Garage, Ceph RGW) and watching for the "accepts the headers but ignores the condition" failure the docs warn about.
- **What does a DO write actually cost at the study's expected rate?** celld's ~90 ms single-node write and the cluster mode's bucket-sync-per-write are both storage-latency-bound. Settled by: a benchmark of a realistic DO workload (e.g. one write per chat message) against R2 vs S3 vs a local MinIO, at 1 node and 2 nodes.
- **Is there a production k8s operator for any of this?** I found none in GitHub repo search; a private/enterprise one may exist. Settled by: searching Helm Hub/Artifact Hub for `workerd` and `celld`, and asking on the Deno Discord.
- **Does `@cloudflare/containers` / `@cloudflare/sandbox` on celld survive the DO rebalance?** celld says hibernatable WebSockets close with 1012 when a cell moves and the container is "supervised by a Durable Object"; what happens to a running container when its cell is rebalanced is not stated in the docs I read. Settled by: reading `docs/services/containers.md` in full and testing a rebalance with a live container.
- **"OpenWorkers" (HN item 46454693, "Self-hosted Cloudflare workers in Rust")** — appeared in search results but I did not fetch it; it may be a relevant fifth candidate. Settled by: fetching https://news.ycombinator.com/item?id=46454693 and locating its repo.
