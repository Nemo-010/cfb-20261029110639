# Lane 11 — Cloudflare open-source inventory: what can actually run on your own metal

Research date: **2026-10-29**. Every repo fact below came from the GitHub API, the repo's own files at `main`, or `developers.cloudflare.com`, fetched that day. Cloudflare's OSS moves daily — `workerd` cut a release on the morning of this research — so pin versions before acting.

## Verdict

Exactly one piece of Cloudflare's stack is both genuinely self-hostable and load-bearing: **`workerd`**, Apache-2.0, which is the same V8 isolate runtime that serves Workers and which in 2026 grew the two features that used to make it useless as a platform — Durable Object storage on local disk and a Docker-backed `ctx.container` per DO — plus a cluster mode that spreads DOs across processes using an S3-compatible bucket for leases and ownership. Everything else in the inventory is one of three things: a **client** for a Cloudflare-hosted product (`cloudflared`, `@cloudflare/containers`, `@cloudflare/sandbox`), a **dev-time simulator** (`miniflare`, and therefore `wrangler dev`), or a **narrow reusable library** (`pingora`, `quiche`, `boringtun`, `capnweb`, `artifact-fs`). The single most important caveat is that **`workerd` gives you a runtime, not a platform**: the repo's own architecture notes call the server "single-tenant" and state that it carries "the unlimited `LimitEnforcer`" and "the null `IsolateLimitEnforcer`", its KV/R2/Queue bindings are HTTP shims to services *you* must write (there is no D1 binding at all), and its Docker container engine is explicitly "only used for local development and testing purposes". The second most important caveat is timing: **cluster mode merged into `main` at 2026-10-29T03:11Z, roughly two hours after the latest release `v1.20261029.1` was cut, so no shipped binary contains it** — it exists only as source today, gated behind `--experimental`, with unencrypted inter-node traffic. Read the inventory as: workerd is a credible answer for the "Workers-compatible edge runtime" and "Durable Objects" slots, and it is not an answer for the "heavy CI container" slot, which needs a real orchestrator (lanes 04/05).

## Findings

### workerd is the only real self-hostable runtime, and it is far more capable in 2026 than its reputation

`workerd` is a JS/Wasm server runtime, "based on the same code that powers Cloudflare Workers" (VERIFIED, https://github.com/cloudflare/workerd). It is Apache-2.0, 9,093 stars, 827 open issues, and releases essentially daily: `v1.20261029.1` published 2026-10-29T00:53:29Z (VERIFIED, GitHub API). You do **not** need Bazel to use it — GitHub releases ship prebuilt `workerd-linux-64.gz`, `workerd-linux-arm64.gz`, `workerd-darwin-64/arm64.gz` and `workerd-windows-64.gz`; the Linux x64 asset is **42,657,326 bytes** compressed (VERIFIED, `content-length` on the release asset) and 148,776,325 bytes unpacked on npm (VERIFIED, https://registry.npmjs.org/@cloudflare/workerd-linux-64). Bazel is only for building it yourself.

Four capabilities matter for this study, all present in `src/workerd/server/workerd.capnp`:

1. **Durable Objects with local-disk SQLite.** `durableObjectStorage` is a union of `none`, `inMemory` and `localDisk`, where `localDisk` creates one `.sqlite` per object. The field carries the marker **"EXPERIMENTAL; SUBJECT TO BACKWARDS-INCOMPATIBLE CHANGE"** (VERIFIED, capnp lines ~876-892).
2. **Containers attached to DOs.** `durableObjectNamespaces.container @5 :ContainerOptions` — "If present, Durable Objects in this namespace have attached containers. workerd will talk to the configured container engine to start containers for each Durable Object … The Durable Object can access the container via the ctx.container API." (VERIFIED, capnp line 795).
3. **Dynamic workers.** A `workerLoader` binding gives Worker code the ability to load further Workers at runtime, with a name-keyed cache — the primitive any multi-tenant Workers platform needs (VERIFIED, capnp line 578).
4. **Cluster mode.** `Config.cluster` — "workerd instances can work together in a cluster, to distribute Durable Objects among them. Each Durable Object runs on one instance at a time, its owner; any instance routes requests for it there. The cluster's shared state lives in an S3-compatible bucket: each instance renews a lease record naming its address, and each Durable Object's owner is a record claimed by a conditional write. Taking an object over from an owner whose lease expired bumps its ownership epoch." (VERIFIED, capnp lines 104-124). The implementation is a Rust crate at `src/workerd/server/cluster/` with `owner.rs`, `ownership.rs`, `s3.rs`, `log.rs` (VERIFIED, repo contents).

Cluster mode is brand new and unreleased. The commit `aa494794` "Cluster workerd processes over a shared bucket (#7994)" is dated **2026-10-29T03:11:42Z** (VERIFIED, commits API); `grep -c ClusterConfig` returns **0** in `workerd.capnp` at tag `v1.20261029.1` and non-zero at `main` (VERIFIED, raw file at both refs). The config field itself says "Requires `--experimental`". It also says, of the inter-node listener: "its traffic is not encrypted: only the cluster's instances should reach it, on a private network (a VPC, WireGuard, Tailscale). A public IP is refused unless `unsafePublicAddress` is set." That is a usable design — the study already has WireGuard-shaped options from lane 06 — but it is not a turnkey distributed object store.

### What workerd deliberately does not include — the part that decides your build cost

These are the load-bearing negatives, and Cloudflare states most of them outright.

- **Not a sandbox.** README: *"WARNING: `workerd` is not a hardened sandbox"* and *"`workerd` on its own does not contain suitable defense-in-depth against the possibility of implementation bugs. When using `workerd` to run possibly-malicious code, you must run it inside an appropriate secure sandbox, such as a virtual machine."* (VERIFIED, https://github.com/cloudflare/workerd). The original launch post has a whole section, *"workerd is not a Secure Sandbox"*, adding that Cloudflare's own defenses *"rely on non-portable kernel features and assumptions about the host system to enforce security and resource limits. All of this is very specific to our environment, and cannot be packaged up in a reusable way."* (VERIFIED, https://blog.cloudflare.com/workerd-open-source-workers-runtime/).
- **Single-tenant, with no per-tenant limits.** The repo's own architecture note describes `server/` as *"the `workerd-server` crate: the single-tenant server"*, and continues: *"It also keeps the single-tenant policy objects, which live in this directory because the production runtime supplies its own: the unlimited `LimitEnforcer`, the clock-corrected `TimerChannel`, the null `IsolateLimitEnforcer`, the default observers."* (VERIFIED, https://github.com/cloudflare/workerd/blob/main/src/workerd/server/AGENTS.md). Translation: there is no CPU-time cap, no memory cap, and no isolate-limit enforcement in the open-source server. If you host other people's Workers, you must build that.
- **No KV, R2, Queue or D1 implementations.** `kvNamespace @11 :ServiceDesignator` — *"A KV namespace, implemented by the named service. … Requests to the namespace will be converted into HTTP requests targeting the given service name."* `r2Bucket @12 :ServiceDesignator` — *"Similar to KV namespaces, this turns operations into HTTP requests aimed at the named service."* `queue @15` likewise (VERIFIED, capnp lines 524-542). The runtime gives you the JS-visible API surface and nothing behind it. **There is no `d1` binding at all in the config schema** — `grep -i d1` over `workerd.capnp` returns nothing (VERIFIED). The internal HTTP protocol those shims speak is not documented anywhere in the repo (BELIEVED; I found no spec).
- **No control plane.** No deploy API, no accounts, no per-host routing, no TLS certificate issuance, no billing, no autoscaling, no node placement. Config is a Cap'n Proto file read at start; `--watch` re-reads it; `--control-fd` emits `listen` events as JSON lines so a supervisor can learn the bound ports (VERIFIED, AGENTS.md). That is the entire integration surface.
- **No observability endpoint.** What exists is tail workers, structured JSON logging, and `--control-fd`. No Prometheus metrics, no traces (BELIEVED — I found no metrics surface in the schema or docs).
- **The Wrangler-config entry point is a stub.** `workerd serve wrangler.jsonc` accepts a Wrangler config, but *"The supported fields are `name`, `main`, `compatibility_date`, `compatibility_flags`, `vars`, `durable_objects`, `migrations`, `no_bundle` and `$schema`; any other field is an error."* (VERIFIED, workerd README). Nine fields. No KV, no R2, no queues, no containers, no cluster. Anything real has to be written in Cap'n Proto by your own tooling.
- **The container engine is a dev tool.** `containerEngine` is a union of `none` and `localDocker`, and `localDocker` is documented as *"Use local Docker daemon for container operations. Only used for local development and testing purposes."* (VERIFIED, capnp line ~918). There is no containerd, Kubernetes, Firecracker or Nomad backend. So `ctx.container` on self-hosted workerd means "shell out to the local Docker socket", which is not how you run a CI fleet.
- **Not an independent project.** *"we cannot promise that external contributions will sit on a level playing field with internal ones … we cannot make any guarantee that those interfaces won't completely change on a whim. If you are trying to build on top of workerd internals, you will need to be prepared either to accept a fair amount of churn, or pin to a specific version."* (VERIFIED, launch blog). And, decisively: *"workerd is not an off-the-shelf edge compute platform"* (VERIFIED, same post, section heading).

### miniflare is the missing platform layer — but it is a simulator, not a server

The standalone `cloudflare/miniflare` repo is **archived** (archived: true, last push 2025-03-13, last release `v2.14.4` on 2024-10-07 — VERIFIED, GitHub API). Miniflare now lives at `packages/miniflare` in `workers-sdk`, declares MIT, and is at `5.20261023.2-beta` (VERIFIED, package.json).

This is the most under-appreciated item in the inventory. Miniflare is not just a shim around `workerd`; it contains **open, readable implementations of the platform services workerd lacks**, written as Workers and Durable Objects that run *on* workerd. `packages/miniflare/src/plugins/` has directories for `kv`, `r2`, `d1`, `queues`, `do`, `workflows`, `cache`, `vectorize`, `browser-rendering`, `images`, `hyperdrive`, `ratelimit`, `secret-store`, `vpc-networks` and more (VERIFIED, repo contents), and `src/workers/` holds the service implementations — e.g. `kv/namespace.worker.ts` implements KV on top of `MiniflareDurableObject`, `r2/bucket.worker.ts` is 38 KB of R2 semantics.

So a self-hosted Workers platform built from Cloudflare OSS is not a green field: workerd supplies the runtime, DO storage and containers, and miniflare supplies reference implementations of KV/R2/D1/Queues as DO-backed services you can lift. But the caveats are severe and stated in the code: *"NOTE: 'in-memory' storage is never in-memory. We always back simulator Durable Objects with a disk directory service"* (VERIFIED, `src/workers/shared/object.worker.ts`), and the control endpoints *"allow anyone with access to the Miniflare dev server to run arbitrary SQL queries and read arbitrary blobs"* (VERIFIED, same file). These are single-node, unauthenticated, un-replicated, un-hardened emulations. Taking them to production is a rewrite of the storage, auth and lifecycle layers, not a config change.

### `@cloudflare/containers` and `@cloudflare/sandbox` are client libraries for a Cloudflare-hosted product — they are worth nothing on your metal

`cloudflare/containers` is 278 stars, last push 2026-08-24, release `v0.3.7` on 2026-06-04, and describes itself in `package.json` as *"Helper class for container-enabled Durable Objects"*; the README opens *"A class for interacting with Containers on Cloudflare Workers."* (VERIFIED). It is a TypeScript base class extending `DurableObject` that proxies HTTP/WebSocket traffic to `this.ctx.container` and manages start/stop/sleep. It contains no container runtime, no image handling, no scheduler. The thing it talks to is Cloudflare Containers, which is *"Available on Workers Paid plan"* (VERIFIED, https://developers.cloudflare.com/containers/). Its 2026-06-04 release date and 2026-08-24 last push mean it has been quiet for two months while the underlying product moved.

`cloudflare/sandbox-sdk` is 1,156 stars, `@cloudflare/sandbox@1.0.3` on 2026-10-22, Apache-2.0 (the GitHub API reports `NOASSERTION` because the root `LICENSE` is a symlink to `packages/sandbox/LICENSE`; the actual file is Apache-2.0 — VERIFIED by fetching it). Its README is explicit about the dependency: *"A sandbox is a Durable Object and the Container it starts. The Durable Object starts the instance and runs commands with the Container API on `this.ctx.container`."* (VERIFIED). Cloudflare's own docs say sandboxes are *"Available on Workers Paid plan"* and that *"Each instance is a microVM with its own kernel and network"* (VERIFIED, https://developers.cloudflare.com/sandbox/).

**Neither is a building block for a self-hosted sandbox.** They are the ergonomic layer over a Cloudflare-billed microVM service. The only self-hosted `ctx.container` that exists is workerd's `localDocker`, which is documented as dev-only. If you want Firecracker/gVisor sandboxes on your own metal, these repos teach you the API shape and nothing else.

### `agents`, `computer`, `cloudflare-os`, `vibesdk`: frameworks that assume Cloudflare's platform services

`cloudflare/agents` (MIT, 5,912 stars, `agents@0.31.0` on 2026-10-27) is a real framework — *"Agents are persistent, stateful execution environments for agentic workloads, powered by Cloudflare Durable Objects"* (VERIFIED, README) — and its dependency list is mostly portable (`capnweb`, `cron-schedule`, `partysocket`, `yaml`, `esbuild`). It would run on workerd's DO implementation in principle. But its feature table advertises Email, Voice, Browser Agents, AI model calls, Workflows and MCP, and each of those maps to a Cloudflare product binding that self-hosted workerd does not provide. You would get the state machine and lose half the feature list.

`cloudflare/computer` (MIT, 9,752 stars, `@cloudflare/computer@0.8.0`) is more interesting than its name suggests: *"Cloudflare Computer is a virtual filesystem that lives inside a Durable Object. The Durable Object holds the authoritative state in SQLite and exposes one pluggable execution surface through `workspace.runtime`."* Its three backends are a Container (needs sandboxes), an "isolate shell" (needs Dynamic Workers, i.e. the `workerLoader` binding — which workerd **does** have), and "isolate JavaScript" (same). So the two isolate backends are portable to self-hosted workerd; the container backend is not. Its own README warns *"The package contains work-in-progress and experimental components such as the `ContainerBackend`. These should be considered unsuitable for production use."* (VERIFIED).

`cloudflare/cloudflare-os` (Apache-2.0, 11,608 stars) and `cloudflare/vibesdk` (MIT, 5,444 stars) are full applications built on the Cloudflare stack — useful as reference architectures, useless as components.

### `wrangler` and `workers-sdk`: local dev is real, deploy is Cloudflare-only

`workers-sdk` is Apache-2.0 at the repo level but ships both `LICENSE-APACHE` and `LICENSE-MIT`; the `wrangler` package declares `MIT OR Apache-2.0` and is at `4.155.0` (released 2026-10-28), `miniflare` declares MIT. 4,680 stars, 604 open issues.

`wrangler dev` is a genuinely useful thing you can keep: it drives Miniflare, which drives a local `workerd`. `wrangler deploy` is not: *"Wrangler, the Cloudflare Developer Platform command-line interface (CLI), allows you to manage Worker projects. Wrangler commands use the permissions of the authenticated member or API token."* (VERIFIED, https://developers.cloudflare.com/workers/wrangler/) — it talks to the Cloudflare API, and there is no `--target self-hosted`, no alternative backend, no plugin point. **There is no path from `wrangler deploy` to your own workerd.** The only self-host path is `workerd serve` with a config file, and that entry point supports nine fields.

So a self-hosted platform needs its own deploy tool: take a `wrangler.jsonc`, bundle with esbuild (as wrangler does), and emit Cap'n Proto config plus a config reload. That is real but bounded work — and it is exactly what the `workerLoader` binding plus `--watch` are for.

### `cloudflared` is a client. There is no tunnel server in the repo.

`cloudflared` is Apache-2.0, 16,336 stars, release `2026.10.5` on 2026-10-27. The README's first line is *"Contains the command-line client for Cloudflare Tunnel, a tunneling daemon that proxies traffic from the Cloudflare network to your origins."* And: *"Before you use Cloudflare Tunnel, you'll need to complete a few steps in the Cloudflare dashboard: you need to add a website to your Cloudflare account."* (VERIFIED, https://github.com/cloudflare/cloudflared).

There is no server component. The edge that terminates the QUIC connection, assigns the tunnel a hostname, and routes requests lives inside Cloudflare and is not open source. `cloudflared` is therefore **not** a building block for a self-hosted ingress — it is only the agent half of a Cloudflare-owned service. This matters because it is the single most common misreading of Cloudflare's OSS: people see 16k stars and assume the tunnel is self-hostable. It is not. Lane 06 covers what to use instead if you want a self-hosted overlay.

### The genuinely reusable libraries (small, sharp, no Cloudflare dependency)

These are the pieces worth taking regardless of what else you build:

- **`pingora`** (Apache-2.0, 27,732 stars, `0.9.0` on 2026-09-09). A Rust framework for building proxies, not a proxy. *"Pingora is battle tested as it has been serving more than 40 million Internet requests per second for more than a few years"* (VERIFIED, README). HTTP/1-2 end to end, TLS via OpenSSL/BoringSSL/s2n/rustls, gRPC and WebSocket proxying, graceful reload, load balancing, and `pingora-limits`/`pingora-memory-cache` crates. If the study wants its own edge/ingress in front of machines, this is the strongest single building block Cloudflare has published.
- **`quiche`** (BSD-2-Clause, 12,831 stars) — QUIC and HTTP/3 in Rust, with a C API. The transport under any custom edge.
- **`boringtun`** (BSD-3-Clause, 7,237 stars) — userspace WireGuard in Rust. Relevant if the connectivity layer goes non-Cloudflare (lane 06).
- **`capnweb`** (MIT, 4,029 stars) — object-capability RPC over HTTP/WebSocket. This is the RPC layer workerd's own cluster uses and `@cloudflare/computer` depends on. A credible answer to "how do the control plane and the agents talk".
- **`artifact-fs`** (Apache-2.0, 1,208 stars, pushed 2026-10-21) — a Go FUSE driver, beta, that mounts a git repo as a working tree and hydrates blobs on demand. *"It exposes the tree quickly, then hydrates file contents on demand. That makes it useful for sandboxes, agents, and other short-lived environments where waiting for a full clone is too expensive."* It *"also works with any git repo"*, not just Cloudflare Artifacts (VERIFIED, README). This is directly relevant to CI checkout latency and is the one repo here that solves a problem the study actually has.
- **`tableflip`** (BSD-3-Clause) — graceful process restart in Go, for zero-downtime agent upgrades. **`cfssl`** (BSD-2-Clause) — PKI/TLS toolkit for machine identity. **`lol-html`** (BSD-3-Clause) — streaming HTML rewriter, useful only if you proxy HTML. **`foundations`** (BSD-3-Clause) — Cloudflare's Rust telemetry/logging/metrics foundations, which is what Pingora services use.

### What is simply not there

Nothing under `github.com/cloudflare` is a multi-tenant platform. There is no open-source Durable Objects *service* (the replicated, globally-addressed product), no KV/R2/D1 server, no tunnel server, no Access/ZITI identity proxy, no Containers orchestration or image builder, no Workers control plane, no billing. The ~500 repos the GitHub search surfaces for `org:cloudflare` are overwhelmingly SDKs, docs, apps, and single-purpose libraries. Any plan that assumes "Cloudflare open-sourced the platform" is wrong; they open-sourced the runtime and a set of libraries around it.

## Rejected options

| option | why rejected |
|---|---|
| Using `@cloudflare/containers` or `@cloudflare/sandbox` as the self-hosted sandbox layer | Both are client libraries over a Cloudflare-billed microVM service ("Available on Workers Paid plan"). They contain no runtime. The only self-hosted `ctx.container` is workerd's `localDocker`, documented as "only used for local development and testing purposes". |
| Running `miniflare` as a production server | It says so itself: "a simulator for developing and testing". Its DO storage is a disk directory, and its control endpoints "allow anyone with access to the Miniflare dev server to run arbitrary SQL queries and read arbitrary blobs". No auth, no replication, no limits. |
| Using `cloudflared` as a self-hosted tunnel server | It is a client. The edge that terminates the tunnel is Cloudflare's and not open source; the README requires a Cloudflare account and a zone. |
| `wrangler deploy` against self-hosted workerd | There is no such target. Wrangler commands "use the permissions of the authenticated member or API token" and speak only to the Cloudflare API. You must write your own deploy tool emitting Cap'n Proto. |
| `workerd serve wrangler.jsonc` as the deployment format | Nine supported fields; "any other field is an error". Cannot express KV, R2, queues, containers or cluster. |
| Turning on workerd cluster mode in production today | Merged 2026-10-29T03:11Z, absent from `v1.20261029.1` (the release cut ~2h20m earlier), gated behind `--experimental`, unencrypted inter-node traffic, S3 bucket as a single point of failure. |
| Using workerd's Docker container engine for the CI fleet | `localDocker` is dev-only by documentation; there is no containerd/Kubernetes/Nomad backend, no image builder, no placement, no GPU, no node scheduling. workerd is not an orchestrator — that slot belongs to lanes 04/05. |
| Building the control plane itself on workerd | The server is "single-tenant" with an "unlimited `LimitEnforcer`" and a "null `IsolateLimitEnforcer`". Putting your own orchestration inside a runtime with no tenant limits and no hardened sandbox inverts the security model for no benefit. |
| `serverless-registry` as the artifact registry | It is Workers + R2; you would need a working R2, which is the thing being replaced. It is a demo of the platform, not a component of a replacement. |
| `partykit` / `partyserver` as the coordination layer | DO-only, and the deploy path is Cloudflare. You would be building the platform it assumes, then running an abstraction over it. |
| Assuming "Cloudflare open-sourced the platform" | They open-sourced the runtime and libraries. There is no open-source DO service, KV/R2/D1 server, tunnel server, Access proxy, or Containers orchestrator under `github.com/cloudflare`. |

## Open questions

- **When does cluster mode ship, and in what state?** It merged today, is `--experimental`, and has no docs page, no blog post, and no mention in the release notes. Settle it by watching the next `workerd` release tag for `ClusterConfig` in `workerd.capnp`, and by reading `src/workerd/server/cluster/owner.rs` for the lease/failover semantics.
- **Does the released binary accept `Config.cluster`, or is the code compiled out?** The schema is on `main` only, so today it cannot. Once a release includes it, verify by running `workerd serve --experimental` with a `cluster` block and a local MinIO bucket.
- **What are the KV/R2/Queue binding wire protocols?** The schema says requests become HTTP to a named service but does not specify the API. Miniflare's `src/workers/kv/namespace.worker.ts` and `r2/bucket.worker.ts` are the only reference. Settle it by reading those files and testing a hand-written service against a real Worker.
- **Does OSS workerd enforce *any* memory or CPU limit?** AGENTS.md says "unlimited `LimitEnforcer`" and "null `IsolateLimitEnforcer`", which implies none. Settle it by running an infinite loop in a Worker and watching RSS and wall-clock.
- **Does workerd expose metrics?** I found tail workers, structured logs and `--control-fd`, but no Prometheus/OTLP surface. BELIEVED, not proven. Settle it by `strings workerd | grep -i prometheus` and reading `src/workerd/server/log.rs`.
- **Can `containerEngine.localDocker` point at a remote Docker daemon over TCP?** The field is `socketPath` ("Path to the Docker socket"), which suggests unix socket only. Settle it by passing `tcp://host:2375` and seeing whether it is parsed as a path.
- **Does `ctx.container` work at all in a released workerd binary?** `container @5` is present in `v1.20261029.1`, but I did not run it. Settle it with the `container-client` test suite in `src/workerd/server/tests/`.
- **What is Sandbox's GA status?** The docs say "Available on Workers Paid plan" with no beta badge, but a secondary source ("Cloudflare Agents Week 2026") claims Sandboxes went GA. Irrelevant to self-hosting, relevant only if the study ever compares against the Cloudflare product.
- **Is there a third-party self-hosted Workers platform worth evaluating?** Search surfaced "OpenWorkers", described as a Rust implementation of the Workers programming model that is self-hostable. **I did not verify it** — no repo, licence or maturity check. Settle it by fetching its repo and checking whether it embeds `workerd` or reimplements the API (the latter would be a compatibility trap).
- **What does a workerd-based platform cost in engineering?** The gap list is: auth, per-tenant limits, a deploy API, a router, KV/R2/D1 implementations, image building, and observability. Nobody has published a credible open-source implementation of that stack on top of workerd. Settle it by scoping one sprint against `workerLoader` + `--control-fd` + a Cap'n Proto generator and seeing what breaks.
