# E2B — deep review

## Verdict

**Yes, but only in the sandbox/CI-execution slot — not as the orchestrator of the whole fleet.** E2B is the most complete open-source answer to "run untrusted heavy work in a hardware-isolated VM that starts in ~150 ms and can be paused to object storage", and its single-node Embed distribution is genuinely self-hostable (Apache-2.0, no licence key, `s3://`-compatible storage seam, header-based sandbox routing that drops straight behind a Cloudflare Tunnel). It is the right pick for the *job execution layer* of this stack: Firecracker microVM per CI job or per agent container, resumed from a prebuilt template snapshot, with the management plane split cleanly into `api` (REST) + `orchestrator` (gRPC, per node). It is the wrong pick for anything else here: it is not a general container orchestrator (no long-lived services, no arbitrary compose, no scheduling across a heterogeneous fleet without the enterprise/BYOC build), its own dashboard is a Next.js 16 SSR app that does not fit your Workers constraint, and its multi-node story — plus the persistent-volume content API (`belt`) — is *not in the public repo*. Adopt Embed as the CI sandbox plane on one or a few big KVM hosts behind `cloudflared`; write your own dashboard on Workers against the 7,922-line OpenAPI; do not expect to scale past one node per install without talking to E2B.

## What it actually is

Two repos, one of which matters:

- `e2b-dev/E2B` (the 14 MB clone at `/workspace/.clones/e2b`) — SDKs and CLI only. This is the client surface, not the product.
- `e2b-dev/runtime` (the 37 MB clone at `/workspace/.clones/e2b-runtime`, Go, Apache-2.0, 1,781 stars) — "the runtime behind every E2B stack: Cloud, Enterprise, and your own machine" (VERIFIED via GitHub API). This is the whole backend: control-plane REST API, Firecracker data plane, in-VM agent, edge router, template builder, ClickHouse/Postgres/Redis schemas, and the `embed/` single-machine distribution.

The mental model from `docs/ARCHITECTURE.md:19-26` is worth quoting because it is the whole design: **"A sandbox is a resumed snapshot"** and **"Control plane and data plane are separate."** Templates are pre-booted VM snapshots (memory + disk + VM state) in object storage; "creating" a sandbox restores a snapshot, memory pages arrive lazily on page fault via `userfaultfd`, and the root filesystem is a copy-on-write overlay. Sandbox traffic never traverses the API.

Seven services, per `docs/ARCHITECTURE.md:71-79`:

| Service | Package | Role |
|---|---|---|
| api | `packages/api` | Gin REST control plane, OpenAPI-generated from `spec/openapi.yml`, placement/auth/quota |
| orchestrator | `packages/orchestrator` | per-node Firecracker supervision, create/pause/resume/kill |
| template-manager | `packages/orchestrator` (role) | builds templates from OCI images |
| client-proxy | `packages/client-proxy` | edge router: sandbox URL → node |
| envd | `packages/envd` | in-VM agent, process/filesystem API for SDKs, `:49983` |
| dashboard-api | `packages/dashboard-api` | backend for the web dashboard |
| shared | `packages/shared` | protos, storage clients, telemetry, proxy helpers |

`embed/` is the part that makes this reviewable as a self-hosted product rather than a cloud service: it is a Docker Compose file, three Terraform modules (GCP/AWS/Azure) and a Kustomize base that stand the *whole* stack up on one machine, including Postgres 18.6, Redis 7.4.6, ClickHouse 25.8 and Vector 0.51.1.

## Architecture (with file paths)

**Per-sandbox VM orchestration.** `packages/orchestrator` is 766 Go files. `pkg/sandbox/sandbox.go` alone is 4,788 lines — one `Sandbox` struct owning a Firecracker process, an NBD-backed rootfs device, a uffd memory backend, a network namespace, cgroups, and an envd client. Sub-packages are the mechanisms:

- `pkg/sandbox/uffd/` — the lazy-memory engine. `uffd.go` (523 lines) runs the `userfaultfd` handler; `memory_backend.go` defines the `MemoryBackend` interface (`DiffMetadata`, `Prefault`, `Memfd`, `PeekMemfd`, `ServeStats`) and an optional `CoWExporter` capability that *only* the uffd backend implements. `userfaultfd/` holds the raw `UFFDIO_COPY`/`UFFDIO_WRITEPROTECT` work and the `WP_ASYNC` write-protection path (`async_wp_test.go` exercises the kernel feature). `memory/` maps regions; `prefetch/` warms pages.
- `pkg/sandbox/block/` — the block layer: `memfd.go`, `overlay.go`, `dedup.go`, `cache.go`, `streaming_chunk.go`, `prefetch_tracker.go`. This is how a diff against a template becomes a sparse file.
- `pkg/sandbox/nbd/` — the rootfs is served to Firecracker over NBD, not virtio-blk directly. The README's first prerequisite is `modprobe nbd nbds_max=4096` plus a udev rule to stop inotify watching `nbd*`. Embed pins `NBD_POOL_SIZE: "32"` and warns "at parity the refill loop spins and warns" (`embed/compose/compose.yaml`).
- `pkg/sandbox/snapshot.go` — the pause artifact. `Snapshot` bundles the memfile diff + header, rootfs diff, snapfile, metafile, and two flags that encode real engineering pain: `MemoryExportDeferred` (the CoW-window path, where the memfile diff "can still FAIL after Pause returned", gated by `WaitMemorySealed`) and `FilesystemSnapshot` (rootfs-only snapshots that cold-boot on resume).
- `pkg/sandbox/fc/` — Firecracker API client, snapshot load failure classification.
- `pkg/server/` — the gRPC service. Note the admission gates that exist because the resource is finite: `hugepage_admission.go`, `pause_disk_admission.go`, `pause_envd_admission.go`, `checkpoint_detached.go`, `checkpoint_steps.go`, `prefetch_harvest.go`, `upload_retry.go`, `drain_test.go`. `orchestrator.proto` shows the create payload: `template_id`, `build_id`, kernel/firecracker versions, `huge_pages`, `vcpu`, `ram_mb`, `total_disk_size_mb`, `auto_pause`, `auto_pause_filesystem_only`, `max_sandbox_length` (hours), `allow_internet_access`, `volumeMounts`, `iam` workload tokens.

**Pause/resume, end to end** (`docs/ARCHITECTURE.md:~1005`): API writes a snapshot row, then gRPC `Pause` to the node; the node pauses the VM, snapshots it, diffs memory (dirty-page tracking) and rootfs (CoW cache) against the template, caches locally, and uploads asynchronously with a retry budget. "Once the API acquires the pause transition, the snapshot DB upsert and the node RPC share a detached 80-second budget; the Redis transition key has a 95-second TTL." That is the hard number to design against: **pause is time-boxed to ~80 s**, and a node whose disk cannot hold guest memory + rootfs cache + snapfile refuses the pause before starting (Embed sets `PAUSE_ADMISSION_DISK_HEADROOM_MIB: "1024"`).

**Storage seam.** `packages/shared/pkg/storage/storage_url.go` is the whole integration point, and it is clean: a gocloud.dev-style URL dialect with four schemes (`gs`, `s3`, `azblob`, `file`), where `s3://` accepts `endpoint`, `s3ForcePathStyle`, `region`, `ssetype`, `kmskeyid`. Unknown query parameters are *rejected* so typos fail fast; credentials are refused in URLs and stripped from error messages (`redactedURL`). `storage_aws.go:88-98` wires it: `o.BaseEndpoint = aws.String(spec.Endpoint)`, `o.UsePathStyle = spec.UsePathStyle`, on aws-sdk-go-v2. Role resolution lives in `packages/orchestrator/pkg/cfg/storage.go`: `TEMPLATE_STORAGE_URL` and `BUILD_CACHE_STORAGE_URL`, with the legacy `STORAGE_PROVIDER` / `TEMPLATE_BUCKET_NAME` / `S3_USE_PATH_STYLE` envs converted into the same URL form.

**Edge routing.** `packages/shared/pkg/proxy/host.go` implements two routing modes: host-based (`{port}-{sandboxid}.{domain}`) and header-based (`E2b-Sandbox-Id` + `E2b-Sandbox-Port`). `shouldParseHeaders` only takes the header path when the request host is `localhost`/an IP, **or** when the host begins with `sandbox.`. `packages/client-proxy/internal/proxy/proxy.go:198` uses exactly this function. This detail is the single most important thing in the review for your architecture — see below.

**Self-hosting shape.** `embed/compose/compose.yaml` runs the orchestrator with `network_mode: host`, `pid: host`, `cgroup: host`, `privileged: true`, launched through `nsenter` by a container ("the same pattern E2B's own Kubernetes deployment uses"), with `ORCHESTRATOR_SERVICES: orchestrator,template-manager`, `SERVICE_DISCOVERY_PROVIDER: local`, `LOCAL_ORCHESTRATOR_ADDRESS: 127.0.0.1:5008`, and `TEMPLATE_STORAGE_URL: file:///var/lib/e2b/storage/templates`. So Embed deletes Nomad from the picture: in a normal deployment `packages/api/internal/cfg/model.go:30-98` defaults `ServiceDiscoveryProvider` to `nomad` (or `nomad+kubernetes`), and `packages/nomad-nodepool-apm` is the autoscaler plugin.

## The seam into this design

This is the rare candidate whose seams line up with your constraints almost one-for-one.

**Object storage (vs R2) — direct, no adapter needed.** Point `TEMPLATE_STORAGE_URL` and `BUILD_CACHE_STORAGE_URL` at your SeaweedFS/RustFS:

```
TEMPLATE_STORAGE_URL=s3://e2b-templates?endpoint=http://seaweedfs:8333&s3ForcePathStyle=true&region=us-east-1
BUILD_CACHE_STORAGE_URL=s3://e2b-buildcache?endpoint=http://seaweedfs:8333&s3ForcePathStyle=true&region=us-east-1
```

Four caveats, all readable off `storage_url.go`: (1) **bucket only — "key prefixes are not supported"**, so one bucket per role, not one bucket with prefixes; (2) credentials come from `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` in the environment, never the URL; (3) `region` must be set to something the SDK accepts even for a non-AWS backend; (4) do **not** set `ssetype` — the client sends `x-amz-server-side-encryption` on every write, which S3-compatible servers may reject. The workload is friendly to an S3-compatible store: `block/streaming_chunk.go` + `storage_cache_seekable*.go` are ranged, chunked reads with a local cache, which is what SeaweedFS is good at.

**Edge runtime (vs Workers) — the dashboard goes on Workers, the data plane does not.** Your hard constraint is that the dashboard stays on Cloudflare Workers. E2B's own dashboard is the wrong vehicle: `e2b-dev/dashboard` is a **Next.js 16 / React 19 / TypeScript** server-rendered app that proxies to two APIs server-side and keeps the team API key in an httpOnly cookie (VERIFIED, dashboard README). It is not a Workers-native app. But you do not need it — `spec/openapi.yml` (7,922 lines) is the contract, and it covers everything a dashboard wants: `/sandboxes`, `/v2/sandboxes`, `/sandboxes/{id}/pause|resume|fork|connect|timeout|network|snapshots`, `/sandboxes/{id}/logs`, `/sandboxes/metrics`, `/templates*`, `/v2/templates/{id}/builds/{buildID}/logs`, `/unstable/builds`, `/nodes`, `/admin/*`, `/api-keys`, `/secrets`, `/volumes`, `/events/webhooks`. A Workers dashboard calling `api:3000` and `dashboard-api:3010` over the tunnel is a normal fetch client against a documented REST API — the cleanest CF-shaped seam in this whole study.

**Cloudflare Tunnel — works, if you name the hostname right.** Embed serves plain HTTP with no TLS of its own (`embed/README.md`, Limitations), which is exactly what you want behind `cloudflared`: the tunnel terminates TLS and the origin stays HTTP. Then:

- Expose `3000` (api) and `3001` (dashboard) and `3002` (client-proxy) through the tunnel; keep everything else dark.
- Give the client-proxy hostname the form `sandbox.<your-domain>` — because `shouldParseHeaders` only enables `E2b-Sandbox-Id`/`E2b-Sandbox-Port` routing when the host is localhost/an IP **or** starts with `sandbox.` (`packages/shared/pkg/proxy/host.go:49-57`). A tunnel hostname like `sandboxes.example.com` will *not* engage header routing and will fall through to `parseHost`, which needs `{port}-{id}.` and will reject the request.
- This removes E2B's `{port}-{id}.e2b.app` wildcard-DNS requirement entirely: no wildcard DNS, no per-sandbox certificate, no Workers wildcard route. `curl -H "E2b-Sandbox-Id: $ID" -H "E2b-Sandbox-Port: 8080" https://sandbox.example.com/` is the whole sandbox ingress story.

**Stateful coordination (vs Durable Objects) — Redis + Postgres, and you must keep both.** Redis holds the running-sandbox set, the routing catalog the client-proxy reads, and caches; Postgres holds teams/templates/builds/snapshots; ClickHouse holds logs (7-day retention) and metrics. There is no DO-shaped seam here, but there is a *good* one for your design: the routing catalog in Redis is what `client-proxy` resolves, and `client-proxy` is the one component you could conceivably replace with a Worker — except a Worker cannot reach your Redis. So keep `client-proxy` behind the tunnel. That is fine; it is a small Go binary, not a Cloudflare service.

**Compute (vs Containers/Sandbox) — this is the slot.** The orchestrator is a plain Go binary on a host with `/dev/kvm`, NBD and hugepages; it needs no Cloudflare anything. It is reached only by the api's gRPC (port 5008) and by client-proxy (port 5007), both of which can live on the same host or reach it over Tailscale/Tunnel-private routing. Workers VPC can reach `api` for control-plane calls.

**What does *not* seam cleanly: sandbox egress.** The orchestrator redirects each sandbox's egress into `hyperloop` (5010) and three TCP-firewall proxies (5016 HTTP / 5017 TLS / 5018 other) *inside the sandbox's network namespace*, all unauthenticated and machine-local by design. If you wanted sandbox traffic to leave through Cloudflare Mesh/VPC, that is a new egress integration, not a config change.

## Limits and failure modes

Ordered by how likely they are to bite a heavy-CI deployment.

1. **One machine, no HA, and a restart is a mass kill.** `embed/README.md`: "Embed is one machine, by design." Worse, `embed/docs/REFERENCE.md`: the orchestrator "is a host process, launched through `nsenter` by a privileged container… **Its launcher ends every sandbox when it stops.**" The launch script "sweeps sandbox cgroups on SIGTERM, because Compose pre_stop hooks do not fire and the orchestrator itself only drains" (`compose.yaml`). Any host maintenance, kernel update, or orchestrator crash takes every running job with it. For long CI jobs this is the dominant risk.
2. **Port 5008 is unauthenticated and owns the machine.** `REFERENCE.md` is admirably blunt: "Port 5008 is the one to guard most. It creates and kills sandboxes and starts template builds; nothing authenticates it… anyone who reaches it has the whole orchestrator." The four egress-proxy ports (5010, 5016-5018) likewise "have no authentication of their own." 13 ports bind `*:`; only 3000/3001/3002 are meant to be reachable. In your topology this is a tunnel-configuration invariant: the tunnel must front 3000/3002 only, never the orchestrator's host network.
3. **Pause is time-boxed and resource-gated.** 80 s budget / 95 s Redis TTL. A sandbox with tens of GB of dirty memory will not pause inside that window, and the disk-headroom admission (`PAUSE_ADMISSION_DISK_HEADROOM_MIB`) will refuse rather than fail midway. Heavy CI jobs are exactly the memory-heavy case.
4. **Sandbox lifetime is bounded by design.** `max_sandbox_length` is in **hours** (`orchestrator.proto` field 14), and the api enforces per-team ceilings (`/unstable/teams/{teamID}/limits`, `/unstable/teams/{teamID}/metrics/max`). This is a product for agent sandboxes that live minutes, not for a 6-hour build. Expect to fight the timeout evictor for long jobs; `auto_pause` + `auto_resume` exist, and `auto_pause_filesystem_only` avoids paying a full memory snapshot, but the orchestrator "does not act on it — the API evictor does."
5. **Hardware requirements are not negotiable.** `/dev/kvm` (hardware virtualisation), `nbd` with `nbds_max=4096`, and 2 MB hugepages sized for your concurrent RAM (`echo 1024 > /proc/sys/vm/nr_hugepages` in the README is 2 GB, for a test). No nested virtualisation means this wants bare metal or a `.metal` instance class; the Terraform modules create a suitable instance for you. (BELIEVED for the general cloud claim; the `/dev/kvm` requirement itself is VERIFIED.)
6. **Template builds are constrained.** `packages/orchestrator/README.md`: distro is resolved from `/etc/os-release` `ID` and only Debian/Ubuntu, the RHEL *rebuilds* (Fedora, CentOS Stream, Rocky, Alma), Arch and Alpine are accepted; **`rhel`, `ol` and `amzn` are rejected**, as are distroless/scratch images. Sandboxes always boot E2B's kernel — `/lib/modules` is empty, no modules loadable, `selinux=0`. If your CI images are Amazon Linux, this is a hard blocker.
7. **Supply chain points at E2B's registry.** Every service image is pinned to `us-docker.pkg.dev/e2b-artifacts/...` and the five Firecracker/kernel/busybox artifacts are fetched and checksum-verified by `compose/scripts/fetch-artifacts.sh` from E2B's bucket. You are self-hosting the *control*, not the *artifacts*. Mirror them.
8. **Observability is deliberately thin.** Logs go to ClickHouse via Vector (7-day retention); metrics only exist if `E2B_OTEL_COLLECTOR_GRPC_ENDPOINT` is set, and the built-in collector "is not an observability stack. Nothing here stores or shows traces, logs or the services' own metrics" — it keeps `e2b.*` metrics and drops the rest. The dashboard's monitoring charts stay empty without it.
9. **Feature-flag fallbacks.** In the cloud build, behaviours come from LaunchDarkly; Embed replaces some with env vars (`LOGS_READ_CONFIG`, `PAUSE_REFUSAL_RESTORE`, `PAUSE_ADMISSION_DISK_HEADROOM_MIB`, `CREATE_MEMORY_REFUSAL`) and notes that "orchestrator releases that predate the knob ignore it." There will be flags you cannot reach.
10. **Plain HTTP and one team.** No TLS, and the auth model is a *single* team API key per install, seeded at first boot, plus `ADMIN_TOKEN` and `SANDBOX_ACCESS_TOKEN_HASH_SEED`. "The admin token is admin over the seeded team on port 3000 without the team API key, including minting and revoking API keys; the team's id is a public constant." Multi-tenancy is not what Embed gives you.

## Rejected / not for this

- **As the fleet orchestrator.** E2B runs Firecracker VMs from prebuilt templates. It does not schedule long-lived services, does not run arbitrary `compose`, and its only multi-node path in the OSS build is `nomad` service discovery plus a nodepool autoscaler plugin — which is precisely the layer this study decided is *not* Cloudflare and probably already has (Nomad/K8s). Do not let E2B become your Nomad.
- **As the object-storage layer.** It is an S3 *client*. It will happily use your SeaweedFS; it will never be it.
- **As the edge/Workers replacement.** `client-proxy` is a Go binary that resolves Redis; it is not a Workers substitute, and replacing it with a Worker breaks the Redis dependency. Keep it behind the tunnel.
- **E2B's own dashboard.** Next.js 16 SSR + httpOnly cookie + server-side proxying. Not Workers-native, and it duplicates a dashboard you already have. Build the Workers dashboard against `spec/openapi.yml`.
- **Persistent volumes.** `POST /volumes` mints a token, but content is served by `belt`, which is not public (404). Treat persistent volumes as unavailable until proven otherwise.
- **Multi-tenant SaaS.** One seeded team, one API key, an admin token that is total control. Fine for an internal CI plane; not fine as a shared service.
- **Amazon Linux / RHEL / UBI CI images.** Rejected by the template builder at build time.

## Open questions

1. **Does `s3://` + SeaweedFS actually survive the template path?** The URL dialect and the aws-sdk wiring are there, but template artifacts use a custom header/block format (`shared/pkg/storage/header`, `block/streaming_chunk.go`) with ranged, possibly multipart reads. Needs a real `Template.build` against SeaweedFS/RustFS with path-style on, before committing. Note the absence of key prefixes: one bucket per role.
2. **What is the actual maximum sandbox lifetime** an Embed install will honour — is `max_sandbox_length` in hours enforced by the api evictor even with `auto_pause` off? This decides whether 6-hour CI jobs are possible at all.
3. **How big a pause is survivable?** The 80 s budget plus disk-headroom admission implies a memory ceiling. Where is it for, say, 16 GB of dirty pages on NVMe?
4. **Is `belt` on a roadmap to open source**, or is persistent volume content permanently enterprise? The api half is public; the data half is not, which is an odd split.
5. **Does the `sandbox.` prefix requirement interact badly with Cloudflare's own hostname handling** (e.g. a `sandbox.example.com` CNAME to `*.cfargotunnel.com` with a Worker route on `example.com/*`)? Worth a spike: `shouldParseHeaders` matches the *request* host, so the tunnel must preserve it verbatim.
6. **What replaces LaunchDarkly flags we cannot reach** in the Embed build — is there a documented list, or is `PAUSE_REFUSAL_RESTORE`-style env vars the whole story?
7. **Restart blast radius mitigation**: is there a drain mode (`server/drain_test.go` suggests yes) that lets the orchestrator hand off or park running sandboxes across a binary upgrade, or is `orchestrator-launch.sh`'s cgroup sweep the only answer?
